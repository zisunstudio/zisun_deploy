## 1. Overview

This document establishes the global architectural standards, payload envelopes, and conventions for the ZISUN RESTful API. Feature-specific API endpoints are documented within their respective `04_features/*.md` files. This document serves as the overarching rulebook for all API implementations.

---

## 2. API Conventions

### 2.1 Base URL & Versioning
- All consumer-facing endpoints must be prefixed with `/api/v1/`.
- All internal admin endpoints must be prefixed with `/api/admin/v1/`.
- Versioning is strictly maintained in the URL path. Breaking changes require a `/v2/` prefix.

### 2.2 Standard Request & Response Envelopes
To ensure client-side predictability (especially for the Next.js BFF layer), all responses must adhere to a standard envelope.

**Success Response (2xx):**
```json
{
  "success": true,
  "data": { ... },
  "meta": { 
    "pagination": { "page": 1, "limit": 20, "total": 145 } 
  } // Optional
}
```

**Error Response (4xx, 5xx):**
```json
{
  "success": false,
  "error": {
    "code": "INSUFFICIENT_STOCK",
    "message": "Only 2 items left in stock for this variant.",
    "details": [ ... ] // Optional Pydantic validation errors
  }
}
```

### 2.3 HTTP Status Codes
- `200 OK`: Standard success for `GET`, `PUT`, `DELETE`.
- `201 Created`: Standard success for `POST` (resource created).
- `400 Bad Request`: Validation failure (e.g., malformed JSON, Pydantic error).
- `401 Unauthorized`: Missing, expired, or invalid JWT.
- `403 Forbidden`: Valid JWT, but insufficient role (e.g., User accessing Admin endpoint).
- `404 Not Found`: Resource does not exist or was soft-deleted.
- `409 Conflict`: Business logic violation (e.g., Optimistic Locking failure, insufficient stock).
- `429 Too Many Requests`: Rate limit exceeded.

## 3. Global Headers

| Header | Usage | Requirement |
|--------|-------|-------------|
| `Authorization` | `Bearer <JWT_ACCESS_TOKEN>` | Required for protected routes. |
| `Content-Type` | `application/json` | Required for all request bodies unless `multipart/form-data`. |
| `X-Idempotency-Key`| Unique UUID v4 generated by client. | Required for critical `POST` mutations (e.g., checkout). |

## 4. Cross-Cutting Concerns

### 4.1 Rate Limiting (FR-01, FR-08)
- **Global limit:** 100 requests / IP / minute.
- **Auth endpoints:** 10 requests / IP / minute.
- Exceeding limits returns `429 Too Many Requests` with a `Retry-After` header.

### 4.2 Pagination
- Standardized offset pagination using `page` and `limit` query parameters.
- Max `limit` per request is strictly capped at `100` to prevent DB overload.
- Default `limit` is `20`.

### 4.3 Validation
- Input validation is strictly enforced at the routing boundary using **Pydantic**.
- No raw string interpolation. SQL injection prevented natively by SQLAlchemy ORM.
